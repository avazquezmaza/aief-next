# Evidence

## Summary

Added `aief close --evidence-from <path>`: reads an already-written JUnit XML test report and
fills in `evidence.md`'s `## Verification` section with its counts, then proceeds with `close`'s
normal readiness checks. AIEF never executes a test, a command, or reaches the network — it only
reads a file the user's own test runner/CI already produced. Three real bugs were found and fixed
during implementation — two in the section-manipulation logic (caught by manual testing before any
automated test was written) and one in test-suite registration (caught by cross-checking the
expected test count).

## Activities Performed

- Read `sdd-model.js`'s evidence-type discipline (ADR-021: only `file_assertion`/`artifact_state`
  supported, `command_result`/`external_reference` rejected as requiring execution/network) before
  designing, to keep this feature inside what the project's own governance already allows — framed
  explicitly in `change.md`'s "Governance note".
- Checked `checkChangeReadiness()`'s evidence classification (`classifyEvidence()`,
  pending-vs-substantive line counting) to confirm this feature only needs to fill in one section
  honestly — it does not, and should not, try to auto-complete Summary/Findings/Risks/
  Recommendations/Lessons Learned, which require judgment a test count can't provide.
- Confirmed the precedent for a CLI command auto-writing part of `evidence.md`: `aief bootstrap`
  already does this for the Adoption Change ("Generated by AIEF during adoption") — this Change
  follows the same shape, clearly labeled as machine-derived.
- Wrote `parseJUnitReport()` (`cli/src/core/domain/junit-report.js`): fixed-regex extraction of
  `<testsuite>` root attributes, summed across every suite found — same "fixed regex, never a
  heuristic parser, never AI" discipline `sdd-model.js` established for Markdown.
- **Bug 1, found by manual testing before writing automated tests**: an initial
  `replaceOrAppendEvidenceSection()` used a single regex with a `(?=\n## |$)` lookahead under the
  `/m` flag (needed for `^` to find the heading). Manually testing the case where the targeted
  section is the *last* one in the file, with a multi-line body, showed `$` matches at every line
  ending under `/m` — silently truncating the body after its first line instead of capturing all of
  it. Fixed by rewriting the section-body lookup as plain string-index arithmetic (`indexOf`), with
  no regex end-of-string ambiguity possible.
- **Bug 2, also found by manual testing**: the first working version special-cased the placeholder
  (`"Pending."` → replace with no sub-heading) and only recognized "this is already my own capture"
  by checking whether the *entire* section body started with the marker text. That broke the moment
  the section had prior human prose: the first capture correctly appended a marked sub-block below
  the prose, but a second capture no longer saw a body *starting* with the marker (the prose was
  still first) — so it appended a second block instead of replacing the first. Reproduced with a
  bootstrap-generated Adoption Change's own real `## Verification` prose (which is exactly this
  shape) before fixing. Fixed by always rendering the capture as its own `### Captured Test Report`
  sub-block (even for the placeholder case) and searching for that sub-block specifically, wherever
  it sits in the body — making "already captured" one check regardless of what precedes it.
- Wired `--evidence-from` into `close()`, reloading the in-memory `change` after the write so the
  existing readiness-check logic sees the update, with zero other lines of `close()` touched.
- Added 13 unit tests (`junit-report.test.js`, `evidence-sections.test.js` — including regression
  tests for both bugs above) and 8 CLI-level tests (`cli.test.js`) covering the valid-report path,
  both error paths, idempotent re-capture from both origins (placeholder and human-prose), the
  `--yes`-combined path, and byte-identical output without the flag.
- Documented the flag in `docs/cli.md` and the `close` entry of `COMMAND_HELP` (`cli.js`).

## Verification

- `node --test cli/tests/junit-report.test.js cli/tests/evidence-sections.test.js`: 13/13 passing.
- `node --test cli/tests/cli.test.js`: 210/210 passing (202 existing + 8 new).
- **Bug 3, found while re-checking the count**: `npm test` (root) delegates to `cli/package.json`'s
  `test` script, which is an **explicit list of test files**, not a glob — `junit-report.test.js`
  and `evidence-sections.test.js` were silently never run by `npm test`/CI until added to that list.
  Fixed by appending both to `cli/package.json`'s `test` script. Caught by cross-checking the
  expected count (778 = 770 + 8 new `cli.test.js` tests, with the 13 new unit tests *not* adding to
  that number) against what actually ran — a mismatch that would otherwise have shipped two
  untested-by-CI files.
- `npm test` (root, full suite, after the `cli/package.json` fix): **791/791 passing**
  (770 existing + 8 new `cli.test.js` tests + 13 new unit tests, now correctly included).
- `node cli/bin/aief.js verify` (full repo) and `--change 0071-evidence-capture-from-junit-report`:
  PASS.
- `git diff --check`: clean.
- Manual end-to-end verification (preceding all automated tests, per this project's own established
  discipline for this kind of change): valid report on a bootstrap-generated Change, re-capture
  after fixing a failing test (idempotent, no duplicate), missing path (exit 1), non-JUnit file
  (exit 1) — all confirmed before writing a single test file.

## Findings

- Both bugs were subtle enough that a reasonable first implementation would have shipped either
  one without deliberately testing the exact edge cases that exposed them (last-section-in-file,
  and re-capture-over-human-prose) — worth treating "does this handle being the last section" and
  "does this handle a second run" as standard checks for any future evidence.md-mutating feature.

## Risks

- None identified for `aief close` without `--evidence-from` (confirmed byte-identical). With the
  flag: the only write is to the targeted Change's own `evidence.md`, gated by an explicit,
  human-typed path argument (same trust model `aief enrich --file <path>` already uses) — no
  execution, no network, no capability-model change.

## Lessons Learned

- Reproducing the target edge cases manually (a real bootstrap-generated Change's own Verification
  prose, and a genuinely-last multi-line section) before writing a single automated test caught two
  real correctness bugs that unit tests written straight from the spec might well have missed,
  since neither spec.md draft anticipated them until manual testing surfaced them — worth continuing
  as standard practice for any Change that mutates existing Markdown content.
