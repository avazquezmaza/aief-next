# Specification

## Goal

A data-backed answer to "does Laya improve AIEF triage?", and, if yes, a domain-tuned model usable
through the opt-in example, without touching the AIEF engine.

## Requirements

### Phase A: Evaluation

#### R1: Evaluation set and split

- One item per `changes/*/change.md` with a non-placeholder `## Objective` (excludes this Change).
- Input: the `## Objective` text, collapsed to one line.
- `change_type` label from `## Type`, normalized: `General`/`Feature`/`Implementation` → `general`,
  `Fix` → `fix`, `Analysis` → `analysis`, `Definition` → `definition`, `Documentation*` →
  `documentation`. Unmappable types are listed and excluded.
- A fixed stratified split, 50 % train / 50 % test, with a recorded seed (changed from 60/40 before
  any run, so `analysis` reaches 5 test items). **The test split is never used for training, prompt
  tuning or threshold fitting.**
- Generated by a committed script in `eval/`; stored as `eval/dataset.jsonl` (`id`, `text`,
  `change_type`, `split`).
- Known bias, recorded: Objectives are written by Change authors and may echo the type.

#### R2: Security labels (blind, human-reviewed)

- The assistant proposes `security_sensitive` (true/false) with a one-line reason per item, using
  the question's definition (authentication, cryptography, secrets, permissions, network
  boundaries), **before** any Laya run on the set; stored as `eval/security-labels.jsonl`.
- A human reviews and approves the labels before any result is interpreted.

#### R3: Zero-shot run and baselines

- One `laya --batch` run, `--model multilingual`, `LAYA_REVISION=reviewed`,
  `examples/laya-triage/questions.json`; raw output in `eval/laya-zero-shot.jsonl`, with versions,
  hardware and wall time.
- Baselines, fixed before the run: majority class; keyword rule (`fix|bug|regression` → fix,
  `analy|assess|investigat` → analysis, `defin` → definition, `doc|readme` → documentation,
  otherwise general).

#### R4: Metrics

- `change_type`: Macro-F1 over scored classes (at least 5 test items: `general`, `fix`,
  `analysis`), per-class precision/recall/support and confusion matrix, for Laya and both
  baselines. Smaller classes are reported, not scored. Never accuracy alone.
- Zero-shot Laya and both baselines are untrained, so they are scored on **all items** (the
  checkpoint uses these figures) and on the test split (the reference for Phase B).
- `security_sensitive`: precision, recall and false-positive rate at thresholds 0.50–0.95 (step
  0.05). The threshold is fitted on the train split (maximize F1 with recall >= 0.8) and reported
  on the test split.

### Checkpoint: pre-registered go/no-go

**Go** to Phase B only if all hold:

1. There is room to improve: zero-shot Laya Macro-F1 on all items is below 0.85 for `change_type`, or
   `security_sensitive` F1 on all items is below 0.85.
2. There is signal: zero-shot Laya beats the majority baseline on Macro-F1 (all items).
3. Training is feasible: a data source for each scored class is identified (train split plus
   synthetic examples), and the owner confirms the external actions in R6.

**No-go:** record the reason, propose no new Change, and close after Phase A. The example stays as
it is, except a proposed (not applied) threshold change.

### Phase B: Fine-tuning (only on go)

#### R5: Training data

- The train split plus synthetic requirement texts per minority class, generated by the assistant
  and listed in `eval/train-synthetic.jsonl` for human review. No test item and no paraphrase of a
  test item.

#### R6: Training run

- The upstream notebook `notebooks/laya_finetune_typed_decisions_2xT4_kaggle.ipynb` at the release
  matching `laya==0.3.22`, starting from `laya-multilingual`.
- **External actions, each needing explicit owner confirmation:** uploading the training data to
  Kaggle; any push of the model to the Hugging Face hub (the notebook's default). Preferred:
  download the tuned model to a local directory and skip the hub push.
- Weights stay outside the repository; the evidence records the training config, data hash and
  model SHA-256.

#### R7: Re-evaluation

- Same test split, same metrics as R4, tuned vs. zero-shot vs. baselines.
- **Pass** if the tuned model beats zero-shot by at least 0.10 Macro-F1 on `change_type` **or**
  0.10 F1 on `security_sensitive`, without being worse than the keyword baseline on `change_type`.

### Phase C: Wiring (only if R7 passes)

#### R8: Opt-in tuned model in the example

- `LAYA_MODEL_PATH` (local directory) switches the example to the tuned model; unset keeps today's
  behavior. The Laya CLI only accepts named checkpoints, so this path uses Laya's Python API
  (`laya.Agent(<dir>)`) through a small runner in `examples/laya-triage/`.
- `SKILL.md` and `README.md` report the measured test metrics and an updated threshold.
- The fallback and resource checks stay unchanged.

## Acceptance Criteria

- [ ] R1: Dataset and fixed split generated by a committed script; exclusions listed.
- [ ] R2: Security labels proposed before any run on the set.
- [ ] (human) Approve the security labels.
- [ ] R3–R4: Zero-shot and baseline metrics reported on the test split.
- [ ] Checkpoint decision recorded against the pre-registered criteria.
- [ ] R5–R7 done, or skipped with the no-go reason.
- [ ] R8 done, or skipped with the reason.
- [ ] Findings Status updated (0143 F4, 0144 F2) and this Change's own table in `evidence.md`.
- [ ] `git grep -i laya -- cli/` empty; `npm test`, `node cli/bin/aief.js verify`, `git diff --check` pass.
- [ ] (human) Review findings, decision and any wiring before close.
